Overview

We built a real-time cloth simulator. The cloth is a grid of point masses held together by structural, shearing and bending springs. Each time step computes gravity and the spring forces, moves the masses with Verlet integration, and keeps every spring within 10% of its rest length. The cloth collides with a sphere, a plane and itself (using a spatial hash), and is rendered with our own GLSL shaders: diffuse, Blinn-Phong, texture, bump and displacement mapping, and mirror reflection.

The main thing we learned is that a few simple local rules are enough to get folds, swings and wrinkles that look like real fabric, and that the look of the cloth depends on the balance between stiffness and weight more than on either one alone.

Part 1: Masses and springs

The model

The cloth is a grid of num_width_points × num_height_points point masses. Each spring remembers its rest length, which is the distance between its two masses when the grid is built, and pulls or pushes them back towards it. We use three kinds of springs, one for each way a cloth can deform:

  • Structural springs link a mass to its left neighbour and to the one above. They resist stretching along the rows and columns.
  • Shearing springs link a mass to its upper-left and upper-right diagonal neighbours. Without them a square cell can flatten into a rhombus without changing any edge length, so the cloth would shear for free.
  • Bending springs link a mass to the one two steps to its left and two steps above. They only change length when the cloth folds between two consecutive cells, so they resist bending out of the plane.

A mass only creates springs towards the left and upwards. The spring to its right neighbour is created when the loop reaches that neighbour, so each spring exists exactly once.

Implementation

Cloth::buildGrid has two loops over the grid.

The first loop creates the point masses, row by row, so that the mass at grid position (x, y) is stored at index y * num_width_points + x (row-major order, which the mesh-building code expects). With \(n\) masses along a side of length \(L\) there are \(n-1\) gaps, so the spacing is \(L/(n-1)\): the first mass is at (0, 0) and the last one exactly at (width, height). For a horizontal cloth every mass has y = 1 and the grid lies in the xz plane. For a vertical cloth the grid lies in the xy plane and each mass gets a small random z offset in [−1/1000, 1/1000]. Without this offset the cloth would be perfectly flat, all forces would stay in its plane, and it could never start to fold. A mass is pinned if its grid indices (x, y) are in the pinned list of the scene file, for example [0,0] and [49,0] in pinned2.json.

The second loop creates the springs. For each mass we add up to six springs, checking first that the neighbour exists:

  • structural: left if x ≥ 1, above if y ≥ 1;
  • shearing: upper-left if x ≥ 1 and y ≥ 1, upper-right if x ≤ num_width_points − 2 and y ≥ 1;
  • bending: two to the left if x ≥ 2, two above if y ≥ 2.

We need two separate loops because a spring stores pointers to its two masses. If we added springs while still pushing masses into point_masses, the vector could reallocate and the pointers we had already taken would no longer be valid.

As a check, we counted the springs for the 50 × 50 grid of pinned2.json: 4900 structural, 4802 shearing and 4800 bending, 14502 in total. This matches what we expect by hand, \(2n(n-1)\), \(2(n-1)^2\) and \(2n(n-2)\) with \(n = 50\).

Problems we ran into

  • We first divided by \(n\) instead of \(n-1\) for the spacing, so the cloth was one cell too short.
  • In the horizontal case we had written Vector3D pos a second time inside the else block. This declared a new variable that hid the outer one, so all horizontal masses ended up at the default position. The compiler does not complain about this.

Part 2: Simulation via numerical integration

Cloth::simulate advances the cloth by one time step \(\Delta t = 1 / (\text{frames per second} \times \text{steps per frame})\). With the default settings (90 and 30) it is called 2700 times per simulated second. Each call computes the forces, integrates the positions, and then limits how far the springs can stretch. The collision code of Parts 3 and 4 runs between the last two steps.

Forces

All point masses have the same mass, \(m = \text{width} \cdot \text{height} \cdot \text{density} / (n_w n_h)\). At the start of each step we reset the force stored in every point mass, otherwise the forces of the previous steps would keep adding up. We then set it to \(m \sum_i a_i\), where the \(a_i\) are the external accelerations given by the simulator (here only gravity).

Next we loop over the springs and skip those whose type is switched off in the GUI. For a spring of rest length \(l\) between masses \(a\) and \(b\), Hooke's law gives

\[ F_s = k_s \left( \| p_b - p_a \| - l \right). \]

We apply \(F_s\) to \(a\) along the unit vector from \(a\) to \(b\), and the opposite force to \(b\). A stretched spring (\(F_s \gt 0\)) pulls its two masses together and a compressed one pushes them apart. For bending springs we multiply \(k_s\) by 0.2, because cloth resists bending much less than it resists stretching.

Verlet integration

Verlet integration does not store a velocity. It uses the previous position instead: \(x_t - x_{t-\Delta t}\) plays the role of \(v\,\Delta t\). With the damping factor \(d\), the update for every mass that is not pinned is

\[ x_{t+\Delta t} = x_t + (1-d)\,(x_t - x_{t-\Delta t}) + \frac{F_t}{m}\,\Delta t^2. \]

In the code we save the current position, compute the new one, and store the saved value in last_position. Pinned masses are skipped. The GUI gives the damping in percent, so we divide it by 100 to get \(d\). The default of 0.2% looks very small, but it is applied 2700 times per second: without any force, less than 0.5% of a velocity would be left after one second (\(0.998^{2700} \approx 0.0045\)).

Limiting the stretch

With forces alone, the springs next to the pinned corners carry the whole weight of the cloth and stretch a lot, which makes it look like rubber. A larger \(k_s\) would help, but very stiff springs make the integration unstable unless the time step is much smaller. Instead we follow Provot (1995) and correct the positions directly after the integration. For every spring longer than \(1.1\,l\) we compute the excess length \(e = \| p_b - p_a \| - 1.1\,l\) and bring the two masses closer along the direction of the spring:

  • if neither is pinned, each one moves by \(e/2\);
  • if one is pinned, the other one moves by \(e\);
  • if both are pinned, we do nothing.

We apply this to all springs, including those whose type is switched off in the GUI.

Problems we ran into

  • Our first loops used PointMass p = point_masses[i]. This makes a copy, so we were updating the forces and positions of temporaries and the cloth did not move at all. Using a reference (PointMass &p) fixed it.
  • We first looped over the masses and assumed six springs per mass. This is wrong on the borders and we read past the end of springs. We now loop over the springs directly.

Effect of the parameters

All the experiments below use scene/pinned2.json (the two top corners are pinned) with the Normal shader. We changed one parameter at a time and left the others at their default values: \(k_s\) = 5000 N/m, density = 15 g/cm², damping = 0.2%. We restarted the simulation with R after each change.

Spring constant \(k_s\)

With a very low \(k_s\) the springs are too weak to hold the weight of the cloth. Ripples run through it while it falls, and at rest the top edge hangs in a deep U with a series of thin wrinkles just below it.

With a very high \(k_s\) the cloth hardly stretches. It swings down almost like a stiff sheet and stays smooth the whole time. At rest the top edge sags only slightly and there is a single wide fold.

Both cloths take about two seconds to come down, so \(k_s\) changes the shape much more than the timing.

Density

Density does roughly the opposite of \(k_s\). A light cloth puts very little load on the springs and stays almost flat, like the high \(k_s\) case. A heavy cloth sags in a deep U with large folds below the top edge, like the low \(k_s\) case, and already folds more during the fall.

The reason is that the acceleration caused by a spring is \(F_s / m\) and \(m\) is proportional to the density, so the shape depends mostly on the ratio \(k_s / \text{density}\). Both cloths fall at about the same speed, since gravity gives every mass the same acceleration.

Damping

Damping does not change the shape at rest, only how the cloth gets there.

With 0% damping the cloth falls fast, overshoots and keeps swinging back and forth, with small waves running across the surface (the uneven shading in the screenshot). The swing dies down very slowly and we never saw the cloth stop completely.

With 1% damping (the maximum of the slider) the cloth comes down slowly and smoothly, as if it were moving through a thick liquid, and stops without swinging past its rest position. It takes about 15 seconds, against about 2 seconds with the default 0.2%.

Part 3: Handling collisions with other objects

Every collision object (sphere or plane) has a collide method that takes one point mass and, if it is inside the object, moves it back out. In Cloth::simulate we call it for every pair of point mass and collision object. This happens after the Verlet integration and before the stretch limit of Part 2, so the springs are corrected after the collisions.

Both objects correct a mass in the same way. We compute a point \(t\) on the surface where the mass should be, and the correction vector from the previous position to it, \(c = t - x_{\text{last}}\). The new position is

\[ x_{\text{new}} = x_{\text{last}} + (1 - f)\,c, \]

where \(f\) is the friction coefficient of the object. We start from last_position and not from the current position because the current position is already inside the object. With \(f = 0\) the mass ends up exactly on the surface. With \(f > 0\) it only covers part of the way, so it moves less along the surface, which is what friction does.

Spheres

A sphere has a center \(o\) and a radius \(r\). A mass at \(x\) collides with it when \(\| x - o \| \le r\). We compare the squared distance with the stored \(r^2\) to avoid a square root, and return right away when the mass is outside.

Otherwise we extend the line from the center through \(x\) until it reaches the surface. That point is the tangent point:

\[ t = o + r\,\frac{x - o}{\| x - o \|}. \]

We then apply the correction above. If a mass sits exactly at the center, the direction \(x - o\) is not defined and we leave it alone. However, this does not happen in practice.

Planes

A plane is given by a point \(p_0\) and a unit normal \(n\). The signed distance \(d(x) = (x - p_0) \cdot n\) tells us on which side of the plane a point is. For a plane, "inside" means that the mass crossed the plane during the last time step, so we compute \(d\) for both the current and the previous position. If they have the same sign, the mass stayed on one side and we do nothing. If the signs differ, or the mass landed exactly on the plane, it collided.

The tangent point is where the mass would hit the plane if it moved straight towards it, which is its projection onto the plane:

\[ t = x - d(x)\,n. \]

We do not move the mass exactly onto \(t\). We use a point a small distance \(\varepsilon\) = SURFACE_OFFSET = 0.0001 away from it, on the side the mass came from:

\[ t' = t + s\,\varepsilon\,n, \qquad s = \text{sign}\big(d(x_{\text{last}})\big). \]

If the mass were placed exactly on the plane, its signed distance would be 0 and in the next step we could not tell which side it belongs to, so it could slip through. The offset keeps it strictly on its original side. The correction is then \(c = t' - x_{\text{last}}\), scaled by \(1 - f\) as above.

Part 4: Handling self-collisions

Without self-collisions the cloth passes through itself when it folds. Checking every pair of point masses would be too slow. Instead we use spatial hashing where we divide space into boxes and only compare masses that are in the same box. In Cloth::simulate, after the Verlet integration, we build the hash table once and then call self_collide on every point mass.

Hashing a position

Cloth::hash_position maps a position to a number that identifies its box. The boxes have size \(w \times h \times t\) with \(w = 3 \cdot \text{width} / n_w\), \(h = 3 \cdot \text{height} / n_h\) and \(t = \max(w, h)\). We get the integer box coordinates with

\[ (i, j, k) = \left( \left\lfloor \frac{x}{w} \right\rfloor, \left\lfloor \frac{y}{h} \right\rfloor, \left\lfloor \frac{z}{t} \right\rfloor \right). \]

We used floor, which gives the same result for positive coordinates but also puts negative coordinates in the correct box. We then combine the three integers into one number:

\[ \text{key} = (i + 64) \cdot 128^2 + (j + 64) \cdot 128 + (k + 64). \]

This key is unique for all boxes within 64 boxes of the origin on each axis, which covers our scenes. Boxes further away could share a key, but that would only add extra candidates, since we check the real distance afterwards.

Building the spatial map

Cloth::build_spatial_map first deletes the vectors from the previous time step and clears the map. It then loops over all point masses, computes the key of each position and appends a pointer to the mass to the vector stored under that key, creating the vector the first time a key is used.

Colliding a point mass

Cloth::self_collide looks up the vector of masses that share the box of the given mass \(p\). Pinned masses are skipped, since they must not move. For every candidate \(q\) other than \(p\) itself we compute the distance \(d = \| p - q \|\). If \(d \lt 2 \cdot \text{thickness}\), the two masses are too close, and we compute the correction that would move \(p\) away from \(q\) until they are exactly \(2 \cdot \text{thickness}\) apart:

\[ c_q = (2 \cdot \text{thickness} - d)\,\frac{p - q}{d}. \]

We average these corrections over all candidates that were too close and divide the result by simulation_steps before adding it to the position of \(p\). Spreading the correction over several steps avoids sudden jumps. If no candidate is too close, \(p\) does not move.

The cloth behaves almost the same as the stiff cloth with \(k_s\) = 50000 N/m, which again matches the \(k_s / \text{density}\) ratio. It folds into a few wide, smooth waves instead of many small wrinkles, lands in a few thick layers that form one large roll, and then opens up with the green side facing up.

At the end one corner stays folded over and the cloth stops moving completely, so the corner never unfolds. This is the stable state. Once the flap lies flat on top of the cloth, gravity presses it down instead of pulling it open. Only the bending springs along the crease push back, and they are too weak to lift the whole flap. Real cloth behaves the same way where a folded corner stays folded unless something pulls on it.

Part 5: Shaders

Shader programs

A shader program is a small program that runs on the GPU as part of the rendering pipeline. Thousands of copies run in parallel, one for each vertex or pixel. A shader program consists of two parts:

  • The vertex shader runs once per vertex. It reads the attributes of the vertex (position, normal, tangent, uv), transforms them from model space to world space, and computes the position on the screen with the view projection. It can also move the vertex, which we use for displacement mapping.
  • The fragment shader runs once per pixel covered by a triangle. Its inputs are the outputs of the vertex shader, interpolated across the triangle with barycentric coordinates. From the position, the normal, the light, the camera and textures it computes the final output color.

Together they describe lighting and materials: the vertex shader provides the geometry, and the fragment shader decides how each point of the surface reacts to the light, for example whether it is matte or shiny, which texture it shows, or whether it reflects its environment. The fragment shader then runs once per pixel-sized fragment, uses the interpolated values and uniforms like the light and camera position, and computes the final color.

Diffuse shading

In Diffuse.frag we implement Lambertian shading based on the following forumla from lecture with its squared length \(r^2\), and the unit normal \(n\):

\[ L_d = k_d\,\frac{I}{r^2}\,\max(0,\, n \cdot l). \]

This is shading that is brightest when the surface faces the light and falls off with distance.

Blinn-Phong shading

The Blinn-Phong model adds up three terms:

\[ L = k_a\,I_a + k_d\,\frac{I}{r^2}\,\max(0,\, n \cdot l) + k_s\,\frac{I}{r^2}\,\max(0,\, n \cdot h)^p. \]
  • The ambient term \(k_a I_a\) is a constant that stands in for the light bouncing around the scene. Without it, the parts facing away from the light would be completely black.
  • The diffuse term is the Lambertian shading from above. It depends only on the angle between the normal and the light.
  • The specular term creates highlights. \(h\) is the half vector, which lies halfway between the direction to the light and the direction to the camera. When \(h\) is close to the normal, the surface reflects the light towards the camera and we see a bright spot. The exponent \(p\) controls how small and sharp the highlight is.

Adding all three gives a colored, shaded cloth with shiny highlights.

Comparison of Bump and Displacement Mapping

For the screenshots below we used textures/texture_4.png, a tile pattern, instead of the default texture_2.png. Both shaders use the same texture. We used normal = 2 and height = 1 for bump mapping, and normal = 100 and height = 0.02 for displacement mapping, as in the handout.

Bump mapping only fakes the bumps, so it changes how the light hits the surface, but the surface itself stays flat. Displacement mapping really moves the surface, so the bumps become part of the shape.

You can see this in our screenshots. With bump mapping the outline of the sphere and the edges of the cloth stay smooth. With displacement mapping the tiles actually stick out of the surface, and the edges and folds of the cloth look uneven and a bit jagged. The difference is easiest to see on the cloth hanging over the sphere. On the sphere alone the difference is small, because the surface only moves a little and the sphere has too few vertices to show the fine tile pattern in its shape. On the cloth, the difference is more pronounced because the displacement is more noticeable on the fabric itself, especially on the edges.

Effect of the sphere resolution

We changed the sphere mesh’s coarseness with -o 16 -a 16 and -o 128 -a 128.

Bump mapping does not depend on the mesh resolution, because the normal is computed per pixel in the fragment shader. With 16 × 16 only the outline of the sphere becomes more polygonal, while the bumps look the same.

Displacement mapping depends on the resolution, because the height is only applied at the vertices. With 16 × 16 the height map is sampled at very few points, so the displaced geometry cannot follow the tiles and becomes coarse and blocky. With 128 × 128 there are many more vertices, so the geometry follows the height map more closely. The shading is the same in both cases, because it comes from the fragment shader. Since the cloth covers most of the sphere in these screenshots and its resolution does not change, the cloth itself looks very similar in all four images.

Custom shader (extra credit)

Our custom shader in Custom.frag turns the cloth into an animated rainbow.

  • Rainbow colors: instead of one color, every point of the cloth gets a color based on where it is on the cloth. The colors change smoothly from one corner to the opposite corner, so the cloth shows a diagonal rainbow.
  • Animation: we pass the current time to the shader. As time goes on, the rainbow slowly slides across the cloth, so the colors keep moving even when the cloth is at rest or the simulation is paused.
  • Color control: the rainbow is tinted by the color picked in the GUI, so the color wheel still has an effect.
  • Lighting: the rainbow is lit with the same Blinn-Phong shading as before, so the folds of the cloth and the shiny highlights are still visible.

To make the animation possible, we added one line to the C++ code that sends the current time to the shader every frame, as a new uniform called u_time.
